# Registry Package

Design 015's [Normative Resolver Registry Package](../../../../design/015-intlify-project-profile-and-locale-policy-design.md#normative-resolver-registry-package) is the fifth authority resolver construction is given. It has six members in fixed roles: three closed schemas, and the Safe Origin Kind, Check, and Finding Registries they admit. This directory holds the revision `"0"` members at the paths 015's Suite Index example uses below the conformance suite's root, `conformance/`. It holds the package's container, the three registries, and their schemas. The Finding Registry has its disclosure policies and one row for each code, with the code's checks, severity, blocking state, subject kinds, reasons, occurrence Evidence, and suggestion kind.

This crate writes every member and the container from its own values, and compiles in only their file digests, which construction compares with the package it is given, as the last row of the construction-failure precedence.

A file digest covers every byte, so these files are kept out of the repository formatter and out of line-ending conversion. Change them only by changing the values and rewriting them.

## Running them

```sh
# every unit test, including the committed bytes and the pinned digests
cargo test -p intlify_config --all-features --lib construction

# rewrite the members and the container after changing a value; it prints
# the digests to pin in src/construction/registry.rs and in
# src/construction/registry/safe_origin.rs, check.rs, and finding.rs
cargo run -p intlify_config --features vectors --example generate_construction_artifacts -- --write

# the committed bytes, and the independent Node checks
vp run construction:check
```

## The Safe Origin Kind Registry

- **Values.** The registry is written from the crate's vocabulary of 015's seven evidence kinds and ten Safe Origin Kinds (`src/resolver/origin.rs`). A row is `{ id, rank, permittedEvidenceKinds }`. The rank is a shortest decimal string, as every ordinal in 015's records is, and the permitted evidence kinds keep the order of 015's table. The table's descriptions of each input boundary are documentation, not registry fields.
- **Schema.** The schema closes the container and every row, and requires each member. It closes the vocabularies: an ID is one of the ten, and an evidence kind one of the seven. A rank is a shortest decimal string, and a row permits at least one evidence kind, none twice. It does not say which rank or which evidence kinds an ID has. The registry's file digest, compiled in, fixes those.
- **Closed graph.** Construction reads the registry it admitted, and refuses one it cannot read as its type, or one in which an ID or a rank repeats, with the row of the registry cross-references.

The Node checker shares no code with this crate. It builds the registry from its own copy of 015's Safe Origin Kind table, checks that the schema closes the container, every row, the IDs, the evidence kinds, and a rank's spelling, hashes both members, and reads the two pinned digests out of the crate's source. It does not read the design document.

## The Check Registry

- **Values.** The registry is written from the resolver's subject kinds and their checks (`src/resolver/subject.rs`), so every `(phase, subject kind, check)` the resolver evaluates has one row, and so does every check of the kinds declared before their units exist. A row is `{ checkId, phaseId, ruleId, subjectKind, subjectKeyStrategy, subjectContentProjection, owningScope, parentSubject, subjectKindRank, checkRank, prerequisiteCheckIds, possibleFindingCodes, possibleEvidenceRecordKinds, ownedDependencies, findingPayloadStrategy }`; `parentSubject` is absent for an unscoped subject.
- **IDs.** 015 leaves the IDs of kinds, scopes, and checks to the registry. A kind's ID is its name in kebab case, such as `relation-endpoint` or `diagnostic-domain`. A check ID reads `<area>.<subject>.<check>`, the area naming the phase, and 015's five examples, such as `locale.default-requested.member`, name the checks they describe. A rule ID is the check ID after `015.`.
- **Keys.** A kind keyed by nothing is a `singleton`, whose owning scope is its own kind. A single-valued field is a `logical-field`, scoped by the entry its path starts from: the root, a profile, a Target ID, or a Group ID in structural admission, and the selected declaration later. A kind keyed by an identity or content is `canonical-identity-or-content` and projects its content as `redacted-structure`, because classifying invalid content as non-secret would expose arbitrary values (015-157); the fallback candidates' positions are `semantic-position`. A kind whose key is scoped by another names that kind's phase and ID as its parent.
- **Prerequisites.** A row's prerequisites are the checks its units wait on: a unit waits on a check whose result it needs, and is then not evaluated without it, or whose result alone names its subjects, and is then not recorded. A row lists, in row order, only the checks no other check it lists already waits on, so a check under the admitted Resource Limit Policy lists every Policy recheck and not the checks of the policy itself. The resolver's tests make each unit of two complete invocations block in turn and compare what then waits with these lists, and every resolution a test runs checks that each unit it leaves not evaluated reaches its causes through them. The kinds declared only list no prerequisite until their units exist, and no row lists a check of structural admission or profile selection yet: the resolver starts from their complete results.
- **Finding codes.** A row's codes are those its units may report, a notice included, in the order of 015's tables: what the resolver's checks report, and for the kinds declared only, what 015 gives their checks. Every evaluation a test runs asserts that each code it records is one its unit's row lists, unless the test made the result up. Each of 015's 48 codes is some row's. Each code names one Finding Registry row, whose checks are exactly the rows that list it.
- **Evidence records and dependencies.** A row's record kinds are the ordinary Evidence record kinds its units may own, by 015's rules, since the records themselves come with Resolution Evidence: every unit owns its evaluation status, in the Entry domain for resolver bootstrap and entry admission and in the Shared one after; a check that reports codes owns Findings in that domain, with their Entry-owned occurrences and evidence index, and in entry admission also the causes of a Shared projection that cannot materialize; the decision table owns both coverage decision records and the evidence index records its Coverage Decision Evidence refers to; and the owners own the dependency records. Reporting finalization owns none: its domains' terminal Finding and state take reserved slots. A row's dependencies are `{ recordKind, id }` pairs: entry admission's first kind owns the four entry slots' records, structural admission's first the eight common and materialized slots', and each semantic group's owner its group's.
- **Payload strategies.** A row's payload strategy is `{ derivation, details }`. `details` names each code the row may report, in their order, with the members of the code's `details` from 015's closed vocabulary, as 015's code tables give them: a stable reason wherever the code's row names reasons, the schema field of the schema codes, the missing slot, the delivery specification's component, and for a bound its subject kind, group, ID, value, total, and the total's relation, or what the policy requires and the capability makes available. It also names the stable reasons the row may report the code with, in the order 015 lists the code's reasons. A code one check reports takes all of its reasons there; where several checks report one code, each lists only the subconditions it decides, so that every check, code, and reason the registry allows is one a check reaches. Phase 9 never finds a specification revision mismatch, which 015 leaves to bootstrap candidate admission. `derivation` is `key-only` where the row's key can stand for distinct raw values: a locale's own key, which spellings share; an artifact's tuple, which bodies share; a coverage rule's content; structural admission's paths, which hold `*`, and its map keys, which a failed key's content stands in for; a singleton whose check sees each occurrence on its own, such as the longest string; and any key under such a parent. Its payloads derive from the key alone, so past a bound it reports the first-over witness `limit + 1` with `at-least`, even for one value (015-157). Elsewhere it is `exact`: the key names one value, whose exact total a bound reports, as a Target ID, Group ID, or Profile ID names one raw ID. Severity, blocking state, and suggestion kind are each code's own and come with the Finding Registry. Every evaluation a test runs asserts that each result carries what its row's strategy gives its code: a reason exactly where the code's details have one, and then one the row lists for the code, a bound's or a shortfall's details exactly where they have their members, and past a bound an exact total only under an `exact` row, and otherwise the smallest witness.
- **Schema.** The schema closes the container, every row, and a parent, and the vocabularies of phases, kinds, strategies, projections, Finding codes, and Evidence record kinds, and it fixes the spelling of check IDs, rule IDs, scopes, and ranks, that a row's prerequisites are check IDs and its codes and record kinds 015's, none twice, that a dependency pairs one of the three dependency record kinds with an ID of its own vocabulary, and that a payload strategy closes its derivation, one of two, and each code's details, whose members and reasons are 015's, none twice. It does not say which values a row has, or whether the rows agree with each other: the registry's file digest, compiled in, fixes the values.
- **Closed graph.** Construction reads the registry it admitted, with the row of the registry cross-references, and refuses one it cannot read as its type or whose rows do not relate as 015 requires: a check ID names one row, under its own rule ID; the rows of one kind in one phase agree on its strategy, projection, scope, parent, and rank; kinds rank uniquely within a phase and checks within a kind; only a kind keyed by an identity or content names a projection; a singleton has no parent; a parent is a kind with rows in the same or an earlier phase, from which following parents ends at an unscoped kind; and a prerequisite names a row once, never one of a later phase or of a kind its phase ranks later, and following prerequisites never comes back to a row; every dependency record is owned by exactly one row, which lists its record kind; and a row's payload strategy names exactly the codes it may report, in their order. A row of the same kind may be an earlier subject's check, so its rank is not compared. Ranks are compared as the spellings the schema fixes. The conventions 015 leaves to the registry, such as ranks counting up from zero, `redacted-structure` over `non-secret-content`, or prerequisites listed minimally in row order, are not part of the graph, and neither is whether the rows are the resolver's own kinds and checks: a closed registry that is not the one compiled in fails construction's last row by its file digest.

The Node checker does not rebuild the rows. It checks that they agree with each other as 015's registry rules require: a rule ID is its check ID under `015.`, check IDs do not repeat, the rows follow phase, kind-rank, and check-rank order, every row of a kind has the kind's shape, ranks count up from zero, only identity and content keys carry a projection and none is `non-secret-content`, a singleton's scope is its own kind, a parent is an identity-keyed kind of the same or an earlier phase, no chain of parents leads back to a kind, every prerequisite names an earlier row, once and in row order, and none is one another listed prerequisite already waits on, a row's codes are 015's, once each and in the order of its tables, every code is some row's, a row's record kinds are 015's, once each and in its order, and exactly the ones 015's ownership rules give its check, every record kind is some row's, every dependency record has exactly one owner that lists its kind, the first singleton kinds of entry and structural admission own the slots' records and a Shared singleton that waits on checks owns each group's, a row's payload strategy names its codes in their order, each with the details 015's code tables give it and, exactly when those carry a reason, some of the code's reasons in 015's order, every reason 015 gives a code is one some row reports it with, a row's strategy derives from its key alone exactly where a singleton's check sees each occurrence on its own, always for structural admission's other keys, and under a parent that does, every phase but profile projection has rows, and 015's five example check IDs name their checks. It checks that the schema closes the container, every row, a parent, a row's prerequisites, codes, record kinds, dependencies, and payload strategy, and the vocabularies with the right spellings, and it compares both members' file digests with the ones pinned in `src/construction/registry/check.rs`.

## The Finding Registry

- **Values.** The registry is written from 015's 48 codes, in the order of its tables, and from the Check Registry. A row is `{ code, allowedCheckIds, severity, blocking, allowedSubjectKinds, allowedReasons, occurrencePrimaryEvidenceKindByCheck, occurrenceRelatedEvidenceKindsByCheck, evidenceDisclosurePolicies, allowedSafeOriginKindsByEvidenceKind, suggestionKind }`. A code's checks are the Check Registry rows that list it, in row order, and its subject kinds are those rows' kinds, in the order they first appear. Its reasons are the ones 015's tables give it, in their order, which are exactly those its checks list. Every blocking code is an `error`; `project-profile-locale-non-canonical`, the one code that blocks nothing, is a `warning` that suggests the exact canonical replacement, and no other code suggests anything.
- **Policies.** Beside the rows, the registry holds one disclosure policy for each of 015's seven evidence kinds, in its order (015-192). A policy is `{ evidenceKind, required, components, paths? }`: the members every Evidence of the kind has, and each component its view can retain, in view order, as a leaf variant of a view member such as `source.redacted` or `value.redacted-logical-path.redacted-member`. A component is `{ component, disclosure, nonSecretWhen?, tokenProjection? }`. A redacted one is `redacted-structure` and names the projection whose Redacted evidence token replaces it. A literal one is `non-secret-literal`, and where its content is not fixed it names the conditions under which that content counts as non-secret: an owner-marked identity, an adapter-classified locator, a schema-defined name, an identifier key, a canonical locale key, a declared Profile ID, a vocabulary identity, or an admitted exact reference. Entry Source Evidence precedes the canonicalization data, so its path members are never canonical locale keys, and only the artifact input has keyed paths. A resolver-input kind's policy also lists the component path shapes some retained Evidence can carry, in Evidence order (015-190), each `{ origin, roles, key? }` with its fixed roles and their ranks: every Specification Input slot; the vocabulary's root and members, the canonicalization data's root, and the artifact collection's root and members, each member with an admitted key and with a redacted one; the verification input's `pins`; and every `policyComparable` bound with the `bootstrapOnly` bounds of `rawInput` and `artifactBootstrap`, 74 shapes in all. No Finding reaches the verification `mode`, the Specification Input's, verification input's, or capability's root, or another `bootstrapOnly` group.
- **Occurrence Evidence.** For each check, in `allowedCheckIds` order, a row names the primary evidence kind of the check's Finding Occurrences, `{ checkId, kind }`, and the related ones, `{ checkId, kinds }`, without repeats and in the order of the seven kinds (015-189). Only `project-profile-reporting-limit-exceeded`, whose terminal Finding has no occurrence, has the primary kind `none`, and then no related kind. For each kind those name, in that order, `evidenceDisclosurePolicies` names the kind's policy, `{ evidenceKind, paths? }`, with a resolver-input kind's shapes, a subset of those its policy pins, in Evidence order, and `allowedSafeOriginKindsByEvidenceKind` names the origins the row allows the kind, `{ evidenceKind, origins }`, in rank order: only a configuration file for the Entry Source Evidence of the four raw-file checks, either configuration entry for other configuration Evidence, either selector boundary for a selector, and for a resolver input exactly its shapes' origins. A table in `src/construction/registry/occurrence.rs` gives each of the 180 check and code pairs its Evidence. Where 015 names it, the table follows: a root-value bound applied before materialization is `entry-source`, an over-limit selector `profile-selector`, and a bound over the materialized configuration `configuration-value`; a selector Finding relates the applicable declarations as one location; the bootstrap's mismatch candidates are related; and each conflicting locale spelling is primary, with the others related. Elsewhere the primary Evidence is where the check observes the value its Finding reports, and the related Evidence every other location it compares with that value, a set counting as one (015-191): the source of an exceeded bound, which is the capability until the Resource Limit Policy is admitted and the admitted Policy after; the configuration reference through which a check reaches a primary resolver input; the `pins` that do not authenticate a candidate; and the collection a reference fails to resolve in. A related record equal to the primary one is omitted (015-193), so a member that only a redacted key names relates no other member. What 015 leaves open is read as plan 025 records it: a total derived from several configuration locations is `configuration-value`, with the bound source alone related; the locale canonicalization data, which validates a spelling rather than being compared with it, is not related; a Target Profile's declared directions and roles are a set its target must belong to; and a hydration relation is primary, with the Target Profiles outside it related. Every Finding Occurrence a test builds (`src/resolver/occurrence.rs`) carries only Evidence its pair allows: the pair's primary and related kinds, an origin it allows the kind, and for a resolver input one of its shapes.
- **Schema.** The schema closes the container, every policy, component, path shape, and role, and every row, requires each member but a policy's paths and a component's classifications and projection, and closes the vocabularies of evidence kinds, members, components, disclosures, classifications, projections, origins, keys, codes, severities, subject kinds, reasons, and suggestion kinds. A policy names at least one member, none twice, and at least one component; its paths, a component's classifications, none twice, and its projection are absent rather than empty or null; a rank is a shortest decimal string. A row names at least one check, by a check ID's spelling, and at least one subject kind, none twice, and no reason twice. Each per-check entry closes over a check ID's spelling and a kind, `none` included for the primary one, or kinds without repeats, and a row has at least one of each; a policy entry closes over an evidence kind and, when present, at least one shape; and an origin entry over an evidence kind and at least one origin, none twice. It does not say which values a policy or a row has, whether the rows relate to the Check Registry's, or whether their occurrence Evidence is 015's: the registry's file digest, compiled in, fixes the values.
- **Closed graph.** Construction reads the registry it admitted with the row of the registry cross-references, after the Check Registry, and refuses one it cannot read as its type, whose policies are not 015's, or whose rows do not relate to the Check Registry's as 015 requires. The policies must be one for each evidence kind in 015's order, with exactly the members and components of the kind's view, each disclosed as above, and with path shapes the Resolver Input Component Path builds, each into an origin the admitted Safe Origin Kind Registry lets the kind use, once each and in Evidence order. For the rows, every code has exactly one row; a code's checks are exactly the Check Registry rows that list it, so that check-to-Finding and Finding-to-check relate symmetrically; and its subject kinds and reasons are exactly those of its checks. The order of a row's checks, kinds, and reasons is the registry's convention, not part of the graph, but the per-check columns follow the checks' order. For the occurrence Evidence, each per-check column lists the row's checks in their order; only the terminal reporting code has `none`, and then no related kind; related kinds follow the admitted order without repeats; the policies and origins name exactly the kinds of the per-check columns, in that order; a resolver-input kind's shapes are ones its policy pins, in Evidence order, and no other kind has any; and the origins are ones the admitted Safe Origin Kind Registry permits the kind, in rank order, and for a resolver input exactly its shapes' origins. Every shape a policy pins must be one some row carries, or Coverage Decision Evidence does, which carries the Coverage Specification input when the safe default is omitted. The verification `mode` and the roots are shapes the Resolver Input Component Path builds, so this check is what keeps a policy from pinning one.

The Node checker builds the rows' severity, blocking state, suggestion kind, and reasons from its own copy of 015's code tables, and their checks and subject kinds from the Check Registry: one row for each code in table order, a code's checks the rows that list it in row order, its kinds theirs in the order they first appear, and its reasons 015's in their order. It builds the policies from its own copy of 015's Evidence views, their components and projections, and the capability bound tables in `scripts/resolution-bounds.mjs`, and checks that no path shape points into an origin its own copy of the Safe Origin Kind table does not let the kind use. It checks the rows' occurrence Evidence as the closed graph does, against the policies and its own copy of that table, that every pinned shape is carried, and the kinds 015 names: `entry-source` for the root-value bounds, `profile-selector` for an over-limit selector, and `configuration-value` related to every selector Finding. It checks that the schema closes the container, every policy, row, and occurrence Evidence entry, and the vocabularies, and compares both members' file digests with the ones pinned in `src/construction/registry/finding.rs`.

## The container

- **Values.** The container is `{ members: { <role>: { identity, revision, digest } } }`, with the six roles in role order. Under each role it lists the member this crate writes for it: the identity and revision the built-in Root Package admits for the role, `intlify-project-profile-<role>` and `"0"`, and the file digest of the member's bytes. This is the tuple 015 gives each role, which the Resolver Construction Input Set and the Suite Index repeat.
- **Pin.** The container's file digest is compiled in, in `src/construction/registry.rs`, as each member's is in its own module. The resolver's dispatch tables, such as a kind's checks, a check's codes, and a code's reasons, are what write the members, so the committed bytes and the pinned digests keep the tables and the package the same. The Suite Index, which pins these digests in 015, comes with a later phase; until then the compiled-in digests stand for it. Construction's last row compares the package it admitted with them: the container's file digest, and each member's.

The Node checker builds the container from its own copy of the six roles and the members' committed bytes, and compares it, key order included, with the committed container, and its file digest with the one pinned in `src/construction/registry.rs`.

## Construction's checks

Construction checks the package it is given in the order of 015's construction-failure precedence, and refuses with the first row that fails. Rows 31 to 41 are the package's:

| Rows | Component | Checks, in order |
| --- | --- | --- |
| 31–35 | Registry Package | Presence; the declared tuple, strict UTF-8 JSON, and the container's envelope schema with exactly the six roles in role order; identity; revision; file digest |
| 36–40 | Each member, in role order | Presence of its bytes; identity; revision; the file digest the container declares; strict UTF-8 JSON, then, for a schema, a root `$schema` naming Draft 7, the Draft 7 meta-schema, and the validator's reading, or, for a registry, validity against the schema its package admitted for it |
| 41 | Registry Package | The registry cross-references |

The identity and revisions each role admits, the container's envelope schema, and the meta-schema are read from the built-in Root Package.

- **One member at a time.** Each member passes all of its rows before the next is checked, so a schema member is admitted before the registry it admits.
- **The admitted schema.** A registry is checked against the schema its own package admitted for its role, not against the one this crate writes. A schema that admits a registry this crate cannot read moves the refusal to row 41; the digests compiled in are compared only by construction's last row.
- **Cross-references so far.** Row 41 reads the Safe Origin Kind Registry and checks that no ID and no rank repeats, reads the Check Registry and checks that its rows form the closed graph above, and reads the Finding Registry and checks that its policies are 015's under the Safe Origin Kind Registry it admitted, that its rows relate to the Check Registry's and give their occurrence Evidence as 015 requires under that registry, and that some Evidence carries every shape the policies pin, as above.
