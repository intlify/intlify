# Registry Package

Design 015's [Normative Resolver Registry Package](../../../../design/015-intlify-project-profile-and-locale-policy-design.md#normative-resolver-registry-package) is the fifth authority resolver construction is given. It has six members in fixed roles: three closed schemas, and the Safe Origin Kind, Check, and Finding Registries they admit. This directory holds the revision `"0"` members at the paths 015's Suite Index example uses below the conformance suite's root, `conformance/`. So far it holds the Safe Origin Kind Registry, the Check Registry, and their schemas. The Finding Registry, its schema, and the package's container come with their own stages.

This crate writes every member from its own values, and compiles in only their file digests, which construction compares with the members it is given, as the last row of the construction-failure precedence.

A file digest covers every byte, so these files are kept out of the repository formatter and out of line-ending conversion. Change them only by changing the values and rewriting them.

## Running them

```sh
# every unit test, including the committed bytes and the pinned digests
cargo test -p intlify_config --all-features --lib construction

# rewrite the members after changing a value; it prints the digests to pin
# in src/construction/registry/safe_origin.rs and check.rs
cargo run -p intlify_config --features vectors --example generate_construction_artifacts -- --write

# the committed bytes, and the independent Node checks
vp run construction:check
```

## The Safe Origin Kind Registry

- **Values.** The registry is written from the crate's vocabulary of 015's seven evidence kinds and ten Safe Origin Kinds (`src/resolver/origin.rs`). A row is `{ id, rank, permittedEvidenceKinds }`. The rank is a shortest decimal string, as every ordinal in 015's records is, and the permitted evidence kinds keep the order of 015's table. The table's descriptions of each input boundary are documentation, not registry fields.
- **Schema.** The schema closes the container and every row, and requires each member. It closes the vocabularies: an ID is one of the ten, and an evidence kind one of the seven. A rank is a shortest decimal string, and a row permits at least one evidence kind, none twice. It does not say which rank or which evidence kinds an ID has. The registry's file digest, compiled in, fixes those.
- **Closed graph.** Construction reads the registry it admitted, and refuses one it cannot read as its type, or one in which an ID or a rank repeats, with the row of the registry cross-references.

The Node checker shares no code with this crate. It builds the registry from its own copy of 015's Safe Origin Kind table, checks that the schema closes the container, every row, the IDs, the evidence kinds, and a rank's spelling, hashes both members, and reads the two pinned digests out of the crate's source. It does not read the design document.

## The Check Registry

- **Values.** The registry is written from the resolver's subject kinds and their checks (`src/resolver/subject.rs`), so every `(phase, subject kind, check)` the resolver evaluates has one row, and so does every check of the kinds declared before their units exist. A row is `{ checkId, phaseId, ruleId, subjectKind, subjectKeyStrategy, subjectContentProjection, owningScope, parentSubject, subjectKindRank, checkRank, prerequisiteCheckIds, possibleFindingCodes, possibleEvidenceRecordKinds, ownedDependencies }`; `parentSubject` is absent for an unscoped subject. The payload strategy comes with a later stage, which adds its member to every row.
- **IDs.** 015 leaves the IDs of kinds, scopes, and checks to the registry. A kind's ID is its name in kebab case, such as `relation-endpoint` or `diagnostic-domain`. A check ID reads `<area>.<subject>.<check>`, the area naming the phase, and 015's five examples, such as `locale.default-requested.member`, name the checks they describe. A rule ID is the check ID after `015.`.
- **Keys.** A kind keyed by nothing is a `singleton`, whose owning scope is its own kind. A single-valued field is a `logical-field`, scoped by the entry its path starts from: the root, a profile, a Target ID, or a Group ID in structural admission, and the selected declaration later. A kind keyed by an identity or content is `canonical-identity-or-content` and projects its content as `redacted-structure`, because classifying invalid content as non-secret would expose arbitrary values (015-157); the fallback candidates' positions are `semantic-position`. A kind whose key is scoped by another names that kind's phase and ID as its parent.
- **Prerequisites.** A row's prerequisites are the checks its units wait on: a unit waits on a check whose result it needs, and is then not evaluated without it, or whose result alone names its subjects, and is then not recorded. A row lists, in row order, only the checks no other check it lists already waits on, so a check under the admitted Resource Limit Policy lists every Policy recheck and not the checks of the policy itself. The resolver's tests make each unit of two complete invocations block in turn and compare what then waits with these lists, and every resolution a test runs checks that each unit it leaves not evaluated reaches its causes through them. The kinds declared only list no prerequisite until their units exist, and no row lists a check of structural admission or profile selection yet: the resolver starts from their complete results.
- **Finding codes.** A row's codes are those its units may report, a notice included, in the order of 015's tables: what the resolver's checks report, and for the kinds declared only, what 015 gives their checks. Every evaluation a test runs asserts that each code it records is one its unit's row lists, unless the test made the result up. Each of 015's 48 codes is some row's. Whether a code names a Finding Registry row, and which reasons it allows, come with that registry.
- **Evidence records and dependencies.** A row's record kinds are the ordinary Evidence record kinds its units may own, by 015's rules, since the records themselves come with Resolution Evidence: every unit owns its evaluation status, in the Entry domain for resolver bootstrap and entry admission and in the Shared one after; a check that reports codes owns Findings in that domain, with their Entry-owned occurrences and evidence index, and in entry admission also the causes of a Shared projection that cannot materialize; the decision table owns both coverage decision records; and the owners own the dependency records. Reporting finalization owns none: its domains' terminal Finding and state take reserved slots. A row's dependencies are `{ recordKind, id }` pairs: entry admission's first kind owns the four entry slots' records, structural admission's first the eight common and materialized slots', and each semantic group's owner its group's.
- **Schema.** The schema closes the container, every row, and a parent, and the vocabularies of phases, kinds, strategies, projections, Finding codes, and Evidence record kinds, and it fixes the spelling of check IDs, rule IDs, scopes, and ranks, that a row's prerequisites are check IDs and its codes and record kinds 015's, none twice, and that a dependency pairs one of the three dependency record kinds with an ID of its own vocabulary. It does not say which values a row has, or whether the rows agree with each other: the registry's file digest, compiled in, fixes the values.
- **Closed graph.** Construction reads the registry it admitted, with the row of the registry cross-references, and refuses one it cannot read as its type or whose rows do not relate as 015 requires: a check ID names one row, under its own rule ID; the rows of one kind in one phase agree on its strategy, projection, scope, parent, and rank; kinds rank uniquely within a phase and checks within a kind; only a kind keyed by an identity or content names a projection; a singleton has no parent; a parent is a kind with rows in the same or an earlier phase, from which following parents ends at an unscoped kind; and a prerequisite names a row once, never one of a later phase or of a kind its phase ranks later, and following prerequisites never comes back to a row; and every dependency record is owned by exactly one row, which lists its record kind. A row of the same kind may be an earlier subject's check, so its rank is not compared. Ranks are compared as the spellings the schema fixes. The conventions 015 leaves to the registry, such as ranks counting up from zero, `redacted-structure` over `non-secret-content`, or prerequisites listed minimally in row order, are not part of the graph, and neither is whether the rows are the resolver's own kinds and checks: a closed registry that is not the one compiled in fails construction's last row by its file digest.

The Node checker does not rebuild the rows. It checks that they agree with each other as 015's registry rules require: a rule ID is its check ID under `015.`, check IDs do not repeat, the rows follow phase, kind-rank, and check-rank order, every row of a kind has the kind's shape, ranks count up from zero, only identity and content keys carry a projection and none is `non-secret-content`, a singleton's scope is its own kind, a parent is an identity-keyed kind of the same or an earlier phase, no chain of parents leads back to a kind, every prerequisite names an earlier row, once and in row order, and none is one another listed prerequisite already waits on, a row's codes are 015's, once each and in the order of its tables, every code is some row's, a row's record kinds are 015's, once each and in its order, and include its status in its phase's domain, every record kind is some row's, every dependency record has exactly one owner that lists its kind, every phase but profile projection has rows, and 015's five example check IDs name their checks. It checks that the schema closes the container, every row, a parent, a row's prerequisites, codes, record kinds, and dependencies, and the six vocabularies with the right spellings, and it compares both members' file digests with the ones pinned in `src/construction/registry/check.rs`.

## Construction's checks

Construction checks the package it is given in the order of 015's construction-failure precedence, and refuses with the first row that fails. Rows 31 to 41 are the package's:

| Rows | Component | Checks, in order |
| --- | --- | --- |
| 31–35 | Registry Package | Presence; the declared tuple, strict UTF-8 JSON, and the container's envelope schema with exactly the six roles in role order; identity; revision; file digest |
| 36–40 | Each member, in role order | Presence of its bytes; identity; revision; the file digest the container declares; strict UTF-8 JSON, then, for a schema, a root `$schema` naming Draft 7, the Draft 7 meta-schema, and the validator's reading, or, for a registry, validity against the schema its package admitted for it |
| 41 | Registry Package | The registry cross-references |

The identity and revisions each role admits, the container's envelope schema, and the meta-schema are read from the built-in Root Package.

- **One member at a time.** Each member passes all of its rows before the next is checked, so a schema member is admitted before the registry it admits.
- **The admitted schema.** A registry is checked against the schema its own package admitted for its role, not against the one this crate writes. A schema that admits a registry this crate cannot read moves the refusal to row 41; the digests compiled in are compared only by construction's last row.
- **Cross-references so far.** Row 41 reads the Safe Origin Kind Registry and checks that no ID and no rank repeats, and reads the Check Registry and checks that its rows form the closed graph above. The Finding Registry is checked against its admitted schema, and the references between registries come with its stage.
