# Conformance suite

This directory is the root of design 015's [Project Profile Resolver Conformance Suite](../../../design/015-intlify-project-profile-and-locale-policy-design.md#conformance-and-fixtures) revision `"0"`. The suite root is the directory that holds the Suite Index, `suite-index-v0.json`, and every path the index names is relative to it.

The Suite Index pins every artifact of the suite with its identity, its revision, a suite-root-relative path, and its file digest. Its schema, `schemas/suite-index-v0.schema.json`, is the conformance runner's trust root: the runner pins the schema's identity and file digest, reads the schema only from that fixed path, and validates the index against it before it follows any path.

This crate writes the schema and the index from its own values, as it writes the construction artifacts. The index pins the Root Package and its members in [`construction/`](./construction/README.md), the construction authorities in [`authorities/`](./authorities/README.md), and the Registry Package in [`registries/`](./registries/README.md). It pins the Case Schema, `schemas/case-v0.schema.json`, the closed form of the suite's five manifest kinds, the same way, and lists each manifest by its ID, path, and file digest in the array of its kind. The forms of the fixtures a manifest names join the Case Schema with the cases that read them. The construction cases are written, with their manifests in `cases/construction/` and their fixtures in `fixtures/construction/`, and so are the input admission cases of the thirteen boundary kinds, in `cases/admission/` and `fixtures/admission/`. The other arrays stay empty until their cases are written. A file digest covers every byte, so these files are kept out of the repository formatter and out of line-ending conversion.

## Running it

```sh
# every unit test of the index, the Case Schema, the cases, and the runner
cargo test -p intlify_config --all-features --lib conformance

# rewrite the schemas, the index, and the cases after a construction artifact
# changes; it prints the two schemas' file digests to pin in
# src/conformance/index.rs and src/conformance/case.rs
cargo run -p intlify_config --features conformance --example generate_conformance_suite -- --write

# open the suite at an explicit index and run its cases: the runner has no
# default index
cargo run -p intlify_config --features conformance --example run_conformance_suite -- crates/intlify_config/conformance/suite-index-v0.json

# the committed bytes, the runner, and the independent Node checks
vp run conformance:check
```

## Opening a suite

The runner is handed the index's path and opens the suite in this order. The first failure stops it with a Conformance harness failure, which is never a construction failure, an input-admission failure, a Finding, or a resolver outcome. It never reads through a symbolic link below the suite root: a link could reach a file outside the suite with the bytes the index declares, so a path that passes through one is `SymbolicLink`.

1. The trust root: the schema at `schemas/suite-index-v0.schema.json` below the suite root has the file digest the runner pins. Otherwise `Missing`, `SymbolicLink`, or `DigestMismatch`.
2. The index is strict UTF-8 JSON and valid against the schema. Otherwise `Missing`, `Malformed`, or `SchemaInvalid`. An index that lacks a member leaves a body it must list unlisted, and is `SchemaInvalid`.
3. The index is a revision-`"0"` index: each member pins the identity, revision, and digests of the artifact this crate is compiled from, and the Root Package's and the Registry Package's roles come in their fixed order. Where a body lies below the suite root is the index's to say, except for the schema's fixed path, and the Profile Specification is pinned by its semantic digest rather than its file digest. Otherwise `NotRevisionZero`.
4. Every manifest is listed once: each array lists its IDs in ascending unsigned byte order, and no ID occurs in two arrays. Otherwise `NotRevisionZero`.
5. The closure: every body the index names has the file digest the index declares, the Profile Specification's body has the semantic digest the index declares, and each manifest is strict UTF-8 JSON, valid against the Case Schema, with the `id` that lists it and the `manifestKind` of its array. Each fixture a construction case or an input admission case names has the digest the case declares, is strict UTF-8 JSON of the form the Case Schema gives it, the latter its boundary kind's, and every body it references outside a decoded JSON value has the digest the fixture declares. A body two references name is read once, and both must declare its digest. Otherwise `Missing`, `SymbolicLink`, `DigestMismatch`, `Malformed`, `SchemaInvalid`, or `NotRevisionZero`.
6. Each input admission case of a boundary kind can run: the construction case its `resolverConstruction` names is listed, constructs, and has the identity the case states, and the harness admits what it admits before the boundary, the capability value of a boundary that reads capability bounds and, under it, the programmatic pair's canonical Snapshot. Failing to establish either invalidates the case, never becoming the boundary's expected reason. Otherwise `InvalidCase`. The two admission steps' kinds are verified as manifests but not run yet.

Steps 5 and 6 go entry by entry: an entry's body, its manifest and fixture, and an input admission case's construction are checked before the next entry's body is read.

A suite that opened runs its cases from what it verified and reads no file again. A construction case constructs from its fixture's input under the built-in construction root, and passes when construction succeeds with the identity the case expects or refuses with the reason it expects, the construction-root bounds' reason with the bound it names. An input admission case evaluates its boundary on its fixture's input under that construction, and passes when the boundary admits the normalized input the case states or refuses with the reason it expects. A case that does not pass is a conformance failure of the implementation, not a harness failure.

A suite-root-relative path is one or more segments joined by `/`, each starting with an ASCII letter or digit and holding only ASCII letters, digits, `.`, `_`, and `-`. No such path is absolute or empty, or holds a `.` or `..` segment, a backslash, a URL's scheme, or a drive.

## Files

| File | Contents |
| --- | --- |
| `suite-index-v0.json` | The Suite Index: the suite revision, the schema, the Root Package with its five members, the four construction authorities with the mapped configuration schema, the Case Schema, the Registry Package with its six members, and the five manifest arrays: the 44 construction cases, the 105 input admission cases of the boundary kinds, and the other three empty until their cases are written |
| `schemas/suite-index-v0.schema.json` | The Draft 7 schema of the index. It closes every object and gives each value its form, and leaves which identity, revision, and digests a member pins to the runner |
| `cases/construction/*.json` | The 44 Resolver Construction Cases: `015-construction-revision-0`, which constructs from the committed input and expects the identity of the committed construction vector, and one for each of the 43 rows of the construction-failure precedence, named by the row's component and check, which expects the row's reason. Each traces its rule ID, `015.construction.<component>.<check>`, and the decisions that state it |
| `fixtures/construction/*.json` | Each case's fixture: the five components as declared tuples and bytes, each body the case does not change a reference to its committed file, and each body it changes a file beside the fixture, `fixtures/construction/<case>/`, or lowercase hexadecimal when it is not strict UTF-8 JSON. A failing case changes only what its row checks, so every row before it holds |
| `cases/admission/*.json` | The 105 Resolver Input Admission Cases of the thirteen boundary kinds, each under `015-construction-revision-0` and the construction vector's identity: for each kind, `015-admission-<kind>-admitted`, which expects the normalized input its fixture states, and one for each row of the kind's failure precedence, 92 in all, named by the row's check, and its reason when the kind has another row of that check, which expects the row's reason. A refusal shows only its first reason, so two rows of a kind that share a reason are told apart only by the inputs made for them, which differ. Each traces its rule IDs, `015.input-admission.<kind>.<reason>`, the admitted case each pair of its kind, and the decisions of its boundary |
| `fixtures/admission/*.json` | Each case's fixture: the capability value, the input, and for the Verification Input its assertion, as the Case Schema gives the kind's form. A failing case changes the admitted case's input, or lowers one capability bound, only where its row looks, so every row before it holds. A raw input that is strict UTF-8 JSON is a file beside the fixtures, `fixtures/admission/<case>/`, and any other raw input lowercase hexadecimal; the locale data cases supply two placeholder payloads, `fixtures/admission/locale-data/`, whose bytes the boundary does not read. The inputs come from the committed vocabulary, envelope, Verification Input, and Snapshot vectors and the committed locale data manifest, which their own checkers verify |
| `schemas/case-v0.schema.json` | The Case Schema: the closed form of the five manifest kinds, with their ID and rule-ID grammars, `traceability`, construction expectations and reasons, the construction input fixture, each boundary kind's input fixture, reasons, and admitted input, the admission steps' failures, Resolver Case entries and relations, Handoff Vectors, and the eight conditional obligations; and its top-level `failurePrecedence`, each boundary kind's ordered `{ check, reason }` rows and a reference to the construction-admission body that holds the construction rows |

The Node checker shares no code with this crate. It reads every JSON file strictly, refusing a repeated member, and reports an unreadable path or a document that is not an object. It checks that the schema closes every object with exactly the keywords of a closed object, that the index holds exactly its own copy of 015's members, roles, identities, and revisions, that every path names a file with the declared digest, that the containers list the digests the index declares for their members, that the Profile Specification has the semantic digest its own framing computes, and that every digest is the one the crate pins in its source. It also checks that each manifest array lists references of its kind, once and in ascending byte order, and that each manifest has the ID that lists it and the kind of its array. For each construction case it checks that the fixture and every body the fixture references have their declared digests, and that the case expects the reason of the construction-admission row its rule ID names, with a bound only for the bounds' row, or, constructing, the committed vector's identity under every rule. For each input admission case it checks the same closure, that the case names a listed construction case with the vector's identity, and that each boundary kind has its admitted case and one case for each row of the Case Schema's `failurePrecedence`, each expecting its row's reason under its pair's rule ID. It derives each admitted case's normalized input from the fixture on its own: a decoded input with its members in byte order, a revision it computes over the bytes with the Profile Specification's revision domain, a Snapshot that is a committed vector with its digest, and a call-site sidecar with its mappings in canonical order.

The Case Schema's Node checker shares no code with this crate either. It checks that the schema admits exactly the five kinds, each a closed object, under its own copy of 015's boundary table, admission slots, owners, unpaired reasons, relation kinds, obligations, and artifact kinds, with the construction reasons and bounds of the committed construction-admission body, the Safe Origin Kinds of the committed registry, the Snapshot bounds of the committed Resolver Capability Specification, and the semantic groups and Snapshot markers of the committed Profile Specification. It also checks that every manifest form and each of its alternatives, the construction input fixture and its components, and each boundary kind's input fixture, is a closed object with exactly its members, the Registry Package's members closed to the roles of the committed container, that each boundary kind's precedence rows take the positions of the general order without going back and list its row's reasons in order, and that the construction precedence is the body the committed Suite Index pins.
