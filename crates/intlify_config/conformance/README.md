# Conformance suite

This directory is the root of design 015's [Project Profile Resolver Conformance Suite](../../../design/015-intlify-project-profile-and-locale-policy-design.md#conformance-and-fixtures) revision `"0"`. The suite root is the directory that holds the Suite Index, `suite-index-v0.json`, and every path the index names is relative to it.

The Suite Index pins every artifact of the suite with its identity, its revision, a suite-root-relative path, and its file digest. Its schema, `schemas/suite-index-v0.schema.json`, is the conformance runner's trust root: the runner pins the schema's identity and file digest, reads the schema only from that fixed path, and validates the index against it before it follows any path.

This crate writes the schema and the index from its own values, as it writes the construction artifacts. The index pins the Root Package and its members in [`construction/`](./construction/README.md), the construction authorities in [`authorities/`](./authorities/README.md), and the Registry Package in [`registries/`](./registries/README.md). It pins the Case Schema, `schemas/case-v0.schema.json`, the closed form of the suite's five manifest kinds, the same way, and lists each manifest by its ID, path, and file digest in the array of its kind. The forms of the fixtures a manifest names join the Case Schema with the cases that read them. The construction cases are written, with their manifests in `cases/construction/` and their fixtures in `fixtures/construction/`, and so are the input admission cases of the thirteen boundary kinds and the two admission steps, in `cases/admission/` and `fixtures/admission/`, the Resolver Cases, in `cases/resolver/` and `fixtures/resolver/`, the Handoff Vectors, in `cases/handoff/`, and the conditional obligations, in `cases/conditional/`. A file digest covers every byte, so these files are kept out of the repository formatter and out of line-ending conversion.

## Running it

```sh
# every unit test of the index, the Case Schema, the cases, and the runner
cargo test -p intlify_config --all-features --lib conformance

# rewrite the schemas, the index, and the cases after a construction artifact
# changes, and remove the case and fixture files it no longer writes; it
# prints the two schemas' file digests to pin in src/conformance/index.rs and
# src/conformance/case.rs, and stops before writing or removing anything when
# a symbolic link sits below cases/ or fixtures/
cargo run -p intlify_config --features conformance --example generate_conformance_suite -- --write

# open the suite at an explicit index and run its cases: the runner has no
# default index
cargo run -p intlify_config --features conformance --example run_conformance_suite -- crates/intlify_config/conformance/suite-index-v0.json

# the committed bytes, the runner, and the independent Node checks
vp run conformance:check
```

## Opening a suite

The runner is handed the index's path and opens the suite in this order. The first failure stops it with a Conformance harness failure, which is never a construction failure, an input-admission failure, a Finding, or a resolver outcome. It never reads through a symbolic link below the suite root: a link could reach a file outside the suite with the bytes the index declares, so a path that passes through one is `SymbolicLink`.

1. The trust root: the schema at `schemas/suite-index-v0.schema.json` below the suite root has the file digest the runner pins. Otherwise `Missing`, `SymbolicLink`, or `DigestMismatch`.
2. The index is strict UTF-8 JSON and valid against the schema. Otherwise `Missing`, `Malformed`, or `SchemaInvalid`. An index that lacks a member leaves a body it must list unlisted, and is `SchemaInvalid`.
3. The index is a revision-`"0"` index: each member pins the identity, revision, and digests of the artifact this crate is compiled from, and the Root Package's and the Registry Package's roles come in their fixed order. Where a body lies below the suite root is the index's to say, except for the schema's fixed path, and the Profile Specification is pinned by its semantic digest rather than its file digest. Otherwise `NotRevisionZero`.
4. Every manifest is listed once: each array lists its IDs in ascending unsigned byte order, and no ID occurs in two arrays. Otherwise `NotRevisionZero`.
5. The closure: every body the index names has the file digest the index declares, the Profile Specification's body has the semantic digest the index declares, and each manifest is strict UTF-8 JSON, valid against the Case Schema, with the `id` that lists it and the `manifestKind` of its array. Each fixture a case names has the digest the case declares and is strict UTF-8 JSON of the form the Case Schema gives it: a construction case's input fixture, an input admission case's its boundary kind's, and a Resolver Case's common input, entry admission input, and expected outcome forms. Every body a fixture references outside a decoded JSON value has the digest the fixture declares. A body two references name is read once, and both must declare its digest. Otherwise `Missing`, `SymbolicLink`, `DigestMismatch`, `Malformed`, `SchemaInvalid`, or `NotRevisionZero`.
6. Each input admission case can run: the construction case its `resolverConstruction` names is listed, constructs, and has the identity the case states, and the harness admits what it admits before the boundary, the capability value of a boundary that reads capability bounds and, under it, the programmatic pair's canonical Snapshot. Failing to establish either invalidates the case, never becoming the boundary's expected reason. Otherwise `InvalidCase`. An admission step's case has no such part: its capability is one of the Common Invocation Input Set's slots, or bounds an entry, and a refusal is the step's own expected result. Each Resolver Case can run the same way: its construction case is listed, constructs, and has the identity the case states, which each of its expected outcomes names too, each side's entry fixture submits through that side's own adapter, and the boundaries admit each paired entry's inputs as its fixtures give them, each candidate the ID its slot fixes, each input one its boundary admits, and each locator canonical, or absent where the fixture gives none. Once every case is listed, each relation of a Resolver Case names a listed Resolver Case under the same construction case that pairs one of the declaring case's sides. Otherwise `InvalidCase`.
7. Each Handoff Vector reproduces its producer: the Resolver Case its `producerCaseId` names is listed, and each of its expected outcomes is checked and gives the vector's facts and bindings, the facts each a semantic group of the outcome's profile view with its complete value, and the bindings exactly the outcome's binding rows whose key a fact holds, in the outcome's order. Otherwise `UnreproducedVector`. Each conditional obligation is inactive: an evaluated activation's state must be the one the harness computes, from the Configuration Schema Authority Set's configuration schema revisions for `015-XV-001` and from the canonicalization specification revision the Profile Specification names for `015-XV-002`, and an active obligation, evaluated or declared, would need the cases its row names, which no revision-`"0"` manifest can name. Otherwise `UnmetObligation`.

Steps 5 to 7 go entry by entry: an entry's body, its manifest and fixtures, and an input admission case's or a Resolver Case's construction and inputs are checked before the next entry's body is read.

A suite that opened runs its cases from what it verified and reads no file again. A construction case constructs from its fixture's input under the built-in construction root, and passes when construction succeeds with the identity the case expects or refuses with the reason it expects, the construction-root bounds' reason with the bound it names. An input admission case evaluates its boundary on its fixture's input under that construction, and passes when the boundary admits the normalized input the case states or refuses with the reason it expects. An admission step's case runs the step on its fixture's slots, and passes when the step admits the set the case states or yields the failures it expects, in their order. A Resolver Case resolves each paired entry under the resolver its construction case builds, each built once, and has an outcome for each: `<id>/<side>` passes when the entry's outcome is its expected outcome, `<id>/<side>/duties` when the outcome breaks none of the harness's duties, each record's owner a unit of its check's Check Registry row, in that row's phase and subject kind, whose row permits the record's kind, no Finding Key twice in a projection, and, for a complete bundle, Coverage Decision Evidence that covers the Bases exactly, and, when both entries are paired and resolve, `<id>/pair` when they agree where 015 makes them agree: in their construction identity always, and once they reach equal Materialized Resolution Input Sets, in their Shared projection and Shared terminal state and, when both bundles are complete, their outcome, profile, and bindings. An entry that the resolver does not resolve, which only a defect of the resolver makes, fails its own outcomes and has no pair. Every Resolver Case's entries resolve before any relation is checked, and each relation has an outcome for each side both cases pair whose two entries resolve, `<id>/relation/<n>/<side>`, the relation's position in its array and the side: it passes when the case's entry stands in the relation's kind to the other case's entry on that side, `profile-equal` or `profile-changed` when both outcomes are checked and their profile views are equal or differ, `invocation-stale` or `invocation-not-stale` when the case's invocation is invocation-stale or fresh against the other's, and `materialized-input-equal` or `materialized-input-changed` when both entries materialized and their Materialized Resolution Input Sets are equal or differ. An outcome that does not pass is a conformance failure of the implementation, not a harness failure. A Handoff Vector and a conditional obligation have no outcome: 020 or another owner verifies a vector's relationship in its own suite, and an obligation waits for what activates it.

A suite-root-relative path is one or more segments joined by `/`, each starting with an ASCII letter or digit and holding only ASCII letters, digits, `.`, `_`, and `-`. No such path is absolute or empty, or holds a `.` or `..` segment, a backslash, a URL's scheme, or a drive.

The Node checker shares no code with this crate. It reads every JSON file strictly, refusing a repeated member, and reports an unreadable path or a document that is not an object. It checks that the schema closes every object with exactly the keywords of a closed object, that the index holds exactly its own copy of 015's members, roles, identities, and revisions, that every path names a file with the declared digest, that the containers list the digests the index declares for their members, that the Profile Specification has the semantic digest its own framing computes, and that every digest is the one the crate pins in its source. It also checks that each manifest array lists references of its kind, once and in ascending byte order, and that each manifest has the ID that lists it and the kind of its array. For each construction case it checks that the fixture and every body the fixture references have their declared digests, and that the case expects the reason of the construction-admission row its rule ID names, with a bound only for the bounds' row, or, constructing, the committed vector's identity under every rule. For each input admission case it checks the same closure, that the case names a constructing case with the vector's identity, and that each boundary kind has its admitted case and one case for each row of the Case Schema's `failurePrecedence`, each expecting its row's reason under its pair's rule ID. It derives each admitted case's normalized input from the fixture on its own: a decoded input with its members in byte order, a revision it computes over the bytes with the Profile Specification's revision domain, a Snapshot that is a committed vector with its digest, and a call-site sidecar with its mappings in canonical order. For an admission step's case it derives the admitted set the same way slot by slot, with an entry's raw bytes as hexadecimal and its locator by 015's rules, and checks that each failure list runs in slot rank, an origin's first and a programmatic entry's values in the boundary table's order, that a refused capability leaves no other value of the common step, a refused Snapshot no identity and revision, and a refused common step at least one failure, and that the common step, a file entry, and a programmatic entry each have an admitted case and a refused one. For each Resolver Case it checks the same closure for its common input, entry, and expected outcome fixtures, that each side's entry fixture submits through that side's own adapter, that its common input submits the committed ICU4X artifact's manifest and a payload at each address that manifest names, each with the committed bytes for that address, and that each expected outcome names the vector's identity, is checked only with a complete bundle, Shared evidence, and no blocking Finding and is otherwise blocked without a profile or bindings, lists one terminal state for each exhausted domain, Entry first, exactly when its bundle is incomplete, each domain with its projection, has Shared evidence exactly when it has no causes, which are its Entry cause records in order, leaves a row without an owner only for an exhausted domain's terminal Finding or the Entry reserve's cause, each last in its array and naming the terminal state's cause, and lists its bindings in ascending byte order of their keys' framing. It also checks that the case traces each check its expected outcomes report under the check's rule, that a file-only case expects no Shared evidence for its file entry, and that paired entries carry one identity and, when both spell one value under one selector, and so reach one Materialized Resolution Input Set, one Shared projection and Shared terminal state, and when both bundles are also complete, one outcome, profile, and bindings. Each relation names a listed case under the same construction case that pairs one of the declaring case's sides, and on each such side a profile relation holds between two checked expected outcomes whose profile views are equal or differ as its kind says, and a materialized-input relation between two expected outcomes that carry Shared evidence. Staleness and the sets' equality are left to the runner, which resolves both entries. Each Handoff Vector names a listed Resolver Case whose every expected outcome is checked, holds whole semantic groups of each such outcome's profile view as its facts and as its bindings exactly the outcome's rows whose key a fact holds, in the outcome's order, and each Group ID selection vector hands over the groups and the targets and expects what the checker's own copy of 015's selection rules concludes from its selectors. Each negotiation vector hands over the canonicalization specification, the negotiation profile, and the targets, is owned by 027, and expects what the checker's own portable lookup concludes, reading each preference's structure from its canonical spelling and taking any other spelling for an invalid preference. Each source-locale vector is 016's and expects the source locale the checker's own reading of 015's rules gives its Intent, and each fallback vector is 020's and expects the complete order its configured sequence gives. The conditional obligations are one manifest for each row of the Case Schema's table, each inactive, and the authority set maps one configuration schema revision and the Profile Specification names canonicalization specification revision `"0"`, so nothing activates an evaluated row.

The Case Schema's Node checker shares no code with this crate either. It checks that the schema admits exactly the five kinds, each a closed object, under its own copy of 015's boundary table, admission slots, owners, unpaired reasons, relation kinds, obligations, and artifact kinds, with the construction reasons and bounds of the committed construction-admission body, the Safe Origin Kinds of the committed registry, the Snapshot bounds of the committed Resolver Capability Specification, and the semantic groups and Snapshot markers of the committed Profile Specification. It also checks that every manifest form and each of its alternatives, the construction input fixture and its components, each boundary kind's input fixture, and the two admission steps' fixtures, the common one's slots and an entry's in their slots' boundary fixture forms, is a closed object with exactly its members, the Registry Package's members closed to the roles of the committed container, that each boundary kind's precedence rows take the positions of the general order without going back and list its row's reasons in order, and that the construction precedence is the body the committed Suite Index pins. For the expected outcome it checks the outcome's container, each projection's arrays, a row without an owner only in the two that end with a reserved record and only for the terminal reporting-limit Finding or a cause naming its key, each code's Finding Key and Finding, its suggestion's closed form included, against the committed Finding and Check Registries, each evidence kind's Evidence and the origins the committed Safe Origin Kind registry permits for it, the profile view's twelve semantic groups and its policy section's bounds, each a string of decimal digits, against the committed Profile Specification, and one semantic dependency per group with the inputs 015 fixes for it, in their order (D15:2517).
