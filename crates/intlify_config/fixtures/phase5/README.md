# Phase 5 fixtures

Design 015's Phase 5, Resolver Construction, Invocation, and Evidence, constructs one immutable resolver from the built-in Resolver Construction Root Package and a Resolver Construction Input Set, admits each input of an invocation at its closed pre-invocation boundary, and runs the resolution phases over the state Phases 3 and 4 build. An invocation returns a checked or blocked outcome with its Resolver Construction Identity, its Findings, its Shared and Entry Resolution Evidence under the reporting bounds, the profile view and its semantic digest, and the Materialized Resolution Input Set a replay reads. The phase also adds four benchmark phases: `profile_resolver_construct`, `profile_evidence_materialize`, `profile_resolve_e2e`, and `profile_resolve_peak_memory`. Plan 025 implements it. This file maps the phase's coverage to the tests that check it, and names what other phases and designs own.

Everything Phase 5 builds is crate-private. No binding or CLI calls the resolver, and there is no public `LocalizationProjectProfile` yet; that is Phase 7's. Live host inspection is Phase 7's too, so Phase 5 exercises the reasons a host produces through the closed report its adapter hands each boundary (D15:3810).

Each name in a "Checked by" column is a test function in this crate. `tests/fixture_matrix.rs` reads this file and fails when a named test is not a test here. A row naming a later phase or another design states an absence that is a decision, not an oversight.

## Running them

```sh
# every unit and integration test, with the ICU4X provider and the measurements
cargo test -p intlify_config --all-targets --all-features

# the construction artifacts, and the vectors an independent reader checks
vp run construction:check
vp run vectors:framing:check
vp run vectors:bounds:check
vp run vectors:verification:check
vp run vectors:snapshot:check
vp run vectors:profile-view:check
vp run vectors:pattern:check
vp run vectors:validator-values:check
vp run vectors:validator-schemas:check

# the duration and memory measurements, produced and re-admitted from disk
vp run bench:config:smoke
```

### How the frozen Evidence vectors were derived

Design 015 asks for frozen vectors computed by an independent implementation (D15:3455). Three of its six families have a Node checker that recomputes them in CI: the Snapshot framing `S` (`vp run vectors:snapshot:check`), the Profile Specification semantic digest (`vp run construction:check`), and the profile view and its digest (`vp run vectors:profile-view:check`). The three families in `fixtures/evidence-records/vectors.json` do not (plan 025 decision 352):

- the source revisions of both revision domains (D15:744);
- the subject and evidence Redacted tokens (D15:2455-2469);
- the accounting view of each ordinary record kind (D15:2473-2519).

A Python script that never reads this crate computed them. It writes `C` from 017's value framing, the field framing and token records from 015, and each accounting view from 015's rules. From the committed registries it reads only each row's strategy, owning scope, projection, severity, and blocking. It also reproduces the six digests the crate pinned before. For the accounting views, the resolver's output decided only which twelve records to freeze; the script wrote each view, and the tests compare the resolver's bytes with it. The script is not in the repository, and CI does not recompute these vectors. A checker that recomputes them is a candidate handoff to Phase 6.
